# Архитектура Adis MVP

## Почему PWA, а не Flutter (сейчас)

На машине разработки нет Flutter SDK, Android SDK, Node и Python, а MVP нужен сразу и для iOS, и для Android. PWA закрывает задачу без сборки и без магазинов: одна кодовая база, установка на главный экран, офлайн. Архитектура повторяет ту, что описана в ТЗ для Flutter, поэтому перенос идёт по слоям 1:1:

| PWA | Flutter (целевой) |
|---|---|
| `js/screens/*` (feature-first) | `lib/features/*/presentation` |
| `js/data/repositories.js` | `lib/features/*/data/repositories` + Riverpod providers |
| `js/api/contract.js` (DTO, ошибки) | Freezed/json_serializable DTO, `ApiException` |
| `js/api/http-client.js` | Dio + interceptors (auth refresh, retry) |
| `js/mock/*` | `MockApi` implementation for dev/demo flavor |
| `js/ui/router.js` | GoRouter с redirect-гардами |
| `css/tokens.css` | `ThemeData` / `ThemeExtension` (Material 3) |
| `A.secureStorage` | flutter_secure_storage |
| `A.bus` | Riverpod invalidate / streams |

## Слои

```
Screens (UI)  →  Repositories  →  ApiClient  →  [Demo: MockServer → Tools → MockDB]
                                              →  [Server: HttpClient → FastAPI AI Backend]
```

- **Screens** не обращаются к API напрямую, только к `A.repo.*`.
- **Repositories** кэшируют данные, сохраняют офлайн-копию и рассылают события `data:*`. Благодаря этому главная, чат, память и задачи всегда синхронны: это одна система данных.
- **ApiClient** выбирает транспорт (демо или сервер), хранит токены через `secureStorage` и не даёт отправить одну и ту же мутацию дважды (in-flight dedupe).
- **HttpClient** отвечает за таймаут, повтор GET-запросов при слабой сети, обновление токена по 401 и разбор SSE-потока `/chat/stream`.

## ИИ-ядро и инструменты

Модель не выполняет SQL и не пишет в базу сама. Она вызывает инструменты (`memory_search`, `memory_save`, `memory_update`, `memory_delete`, `entity_lookup`, `task_create`, `task_update`, `task_complete`, `notification_schedule`, `proactive_suggestion`). На сервере это функции с проверкой прав пользователя.

Поток:
1. Пользователь пишет или говорит.
2. AI Gateway определяет намерение и вызывает инструменты.
3. Ответ приходит потоком, вместе с **карточками-действиями** (`memory_save`, `task_create`).
4. Пользователь подтверждает карточку, и клиент выполняет действие через обычный REST API (`POST /people`, `POST /memory`, `POST /tasks`).
5. Статус карточки сохраняется (`PATCH …/cards/{cid}`).

В демо-режиме шаги 2–3 выполняет `js/mock/ai-engine.js` + `nlu.js` (правила для русского языка: падежи имён, даты, время, повторы). Там же работают те же функции `js/mock/tools.js`, что и REST-эндпоинты мока, поэтому логика не дублируется.

### Память различает
факты, предположения (требуют подтверждения), намерения, планы, события, предпочтения, идеи, знания. У каждой записи есть источник (чат, голос, вручную, агент), цитата, ссылка на разговор и даты создания и изменения.

### Безопасность памяти
- Чувствительные данные (пароли, документы, карты, здоровье) не сохраняются автоматически. Карточка показывает предупреждение.
- По умолчанию всё сохраняется только после подтверждения (настройка «Спрашивать перед сохранением»).
- Неоднозначное сохраняется как «предположение» со статусом «не подтверждено».

## Уведомления
Источник истины — сервер: `notification_schedule` ставит задачу в очередь (Redis/RabbitMQ), а воркер отправляет Web Push / APNs / FCM. `sw.js` уже обрабатывает `push` и `notificationclick`. Пока приложение открыто, `services/notifications.js` дополнительно показывает напоминания, которые подошли по времени.

## Голос
`services/voice.js` — абстракция провайдеров STT/TTS. Сейчас работает провайдер `device` (Web Speech API). Облачный провайдер (Whisper/TTS через AI Backend) подключается за тем же интерфейсом. Если голос недоступен, UI прямо об этом сообщает и предлагает отдельный демо-ввод с пометкой.

## Ошибки, загрузки, офлайн
- Каждый экран показывает три состояния: загрузка (skeleton), ошибка (повторить) и пусто.
- Без сети экран показывает кэш с баннером «Показаны сохранённые данные», а вверху горит индикатор офлайна.
- `ui.guard` блокирует повторное нажатие и показывает понятное сообщение об ошибке.
- `logger.js` вырезает из логов email, телефоны, токены и пароли.
- Для проверки: **Профиль → Подключение → «Имитировать ошибки сети / медленную сеть»**.

## Доступность
rem-типографика и 4 размера шрифта, режим высокого контраста, тёмная тема (в том числе системная), `prefers-reduced-motion`, области нажатия от 48px, aria-метки, голосовое управление.

## Backend (`server/`)

Python 3.12 + FastAPI + SQLAlchemy 2. API живёт под `/v1`, на том же origin сервер раздаёт PWA (`ADIS_SERVE_APP`).

```
routers (HTTP, валидация pydantic)  →  services/store.py (бизнес-логика, всё в рамках user_id)  →  models (SQLAlchemy)
routers/chat.py  →  ai/gateway.py  →  ai/llm.py (OpenAI-совместимый API, tool calling)  |  ai/rules.py + ai/nlu.py (без LLM)
```

- **Аккаунты.** Пароли хранятся как scrypt-хэши. Токены непрозрачные, в базе лежат только их SHA-256. Одна строка `auth_sessions` соответствует одному устройству. Refresh-токен одноразовый: при обновлении ротируются оба токена. Смена пароля завершает остальные сессии. Число попыток входа ограничено (10 за 15 минут).
- **Изоляция данных.** Любой объект достаётся через `Store._get`, который проверяет `user_id`. Чужой id даёт 404, привязка к чужому человеку отбрасывается.
- **Чат.** `prepare_turn` сохраняет сообщение пользователя до генерации, поэтому повтор с тем же `clientMessageId` получает 409. SSE-генератор открывает собственную сессию БД. Если клиент остановил генерацию или пропала связь, сохраняется уже сгенерированная часть с флагом `stopped`.
- **ИИ.** Движок выбирает `gateway.get_engine()`: LLM, если заданы `ADIS_LLM_BASE_URL` и `ADIS_LLM_MODEL`, иначе правила. Инструменты чтения (`memory_search`, `entity_lookup`, `task_list`) выполняются сразу. Инструменты записи (`memory_save`, `task_create`) создают карточки `pending`, а пользователь подтверждает их через обычный REST. Чувствительные данные блокируются на сервере (`nlu.is_sensitive`), даже если модель предложила их сохранить. Ответ помечается `engine` (`rules` или `llm:<model>`).
- **Время.** В базе хранится naive UTC. Клиент передаёт `X-Timezone`, и в этом поясе разбираются фразы вроде «завтра в 10», считаются «сегодня» и повторы задач.
- **База и миграции.** SQLAlchemy-модели (`adis/models.py`) переносимы: SQLite в разработке, PostgreSQL 16 в продакшене (JSON-поля на Postgres хранятся как `JSONB`). Схему ведёт Alembic (`server/migrations`); `init_db()` при старте делает `upgrade head`. Новое изменение схемы: поправить модели → `alembic revision --autogenerate -m "..."` → проверить файл → `alembic check`. Тесты гоняются на обеих СУБД (`ADIS_TEST_DATABASE_URL`).
- **Доставка (`services/worker.py`).** Асинхронная задача внутри процесса API, раз в `ADIS_WORKER_INTERVAL` секунд: задачи с `notify_at <= now` → push «Напоминание» (`notified_at`); события, у которых наступило `start_at − remind_minutes` → push «Скоро…» (`notified_start`; при переносе события напоминание придёт снова); будильники с `min(next_at, snooze_until) <= now` → `ring_at`, push с `Urgency: high`, расчёт следующего срабатывания. Строки берутся через `FOR UPDATE SKIP LOCKED`, поэтому параллельные воркеры не отправят уведомление дважды. Напоминания, просроченные больше чем на 6 часов (сервер был выключен), не отправляются.
- **Push (`services/push.py`).** Web Push с VAPID (RFC 8030/8291) через `pywebpush`. Ключи берутся из `ADIS_VAPID_*` или создаются один раз в `data/vapid.json`. Подписки 404/410 удаляются; после 10 ошибок подряд подписка тоже удаляется. При выходе из аккаунта клиент отвязывает устройство, при входе привязывает его заново. Сервис-воркер показывает уведомление и по нажатию открывает нужный экран (`route`).
- **Будильники (`services/alarms.py`).** Время задаётся по часам в поясе будильника, поэтому переход на летнее время ничего не ломает. `days` — дни недели в нумерации JS (0 — воскресенье). Клиент (`services/alarm-clock.js`) звонит сам, если приложение открыто (WebAudio + вибрация, звук после первого касания экрана), и сообщает серверу `dismiss`/`snooze`. Если звонок уже сработал на клиенте, сервер не звонит повторно.
- **Календарь (`services/ics.py`).** Подписка iCal по секретному токену (`users.calendar_token`, ротация инвалидирует старую ссылку): события + задачи со сроком, `VALARM` из `remind_minutes` → напоминает и сам телефон. Импорт `.ics`: `TZID`/UTC/целый день, `DURATION`, `VALARM`, дедупликация по `UID` (`events.external_uid`), отменённые пропускаются, у повторяющихся берётся первое вхождение.
- **Календарь в чате.** Намерения `event_create`, `calendar_query`, `event_move`, `event_cancel`, `alarm*` (правила в `ai/nlu.py` + `ai/rules.py`, JS-копия в `app/js/mock/` для демо) и инструменты LLM `event_list`, `event_create`, `event_update`, `alarm_set`. Все изменения проходят через карточку `pending`.

Дальше: pgvector (семантический поиск памяти), Redis (лимиты, очереди), RabbitMQ (агенты), S3 (фото и файлы вместо data URL), повторяющиеся события (RRULE), двусторонняя синхронизация с Google Calendar через OAuth.
